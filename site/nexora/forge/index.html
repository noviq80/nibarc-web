Forge

Forge rewrites the ABAP you have, and writes what you never had.

Neither reaches your system until SAP itself says it passed. Forge reads your landscape through one governed lane, decides the fate of every custom object with a person, and turns the answer into code — a rewrite of what exists, or something new from a written requirement. Five stages. The last word is always a human's, and the proof is SAP's own checks, not ours.

01 · Connect

Your production system is never on the table.

Forge reaches SAP only through the Nexora Agent Platform — our own access layer, and the single lane every read and write travels down. It reads freely. It writes only on approval. It refuses production. Each project states plainly what the connection is currently permitted to do, and the system check that proved it.

Read, write and production, stated separately

Not one permission but three, each shown with the check that last proved it. A failed check downgrades what Forge will do, in the open.

Try it without connecting us to anything

Forge runs against an exported copy of your system. Everything read stays readable and the analysis is real — and sync, checks on SAP, approve and activate switch themselves off until a live check passes. The banner saying so never leaves the screen.

Your model, your choice

Model access is a per-project switch, and which model does the work is yours to pick. Landing and scanning need no model at all.

02 · Scan

Four hundred and ninety-five custom objects. Two-thirds of them nobody calls.

Forge reads every custom object, grades it against clean core, and counts how often it actually ran in production from your own SCMON window. The expensive truth usually arrives early: most of the estate is not load-bearing. Retiring something is cheaper than migrating it, and now you can prove which is which.

Twelve questions, answered from your own system.

Not a report you commission. A set of boards that are already true the moment Forge has read the landscape, each one answering a question in plain words.

  • 02What is used, and how much?
  • 03Who starts it — people, jobs or other systems?
  • 04What is slow, and where does the time go?
  • 05How big and how old is the code?
  • 06How clean is it, and what to fix first?
  • 07Who wrote what, and how clean is it?
  • 08Which processes carry the custom code?
  • 09Where do heavy use and unclean code meet?
  • 10What could be retired?
  • 11Where is the code unsafe?
  • 12What uses what, and what moves together?

Forge is equally plain about what it cannot see: how many objects it failed to read, which types carry no ABAP source at all, and which sources it does not support yet. A coverage panel states all of it, beside the answers.

03 · Understand

Every object gets a decision, and every decision gets a name against it.

Keep as is, retire, adapt, replace with standard, or rebuild on clean core. Forge proposes one and says why — in a sentence made of measurements, not adjectives. A person records the real decision, and the form will not submit without a reason.

It tells you how much it actually knows

Every proposal carries an evidence count — read the code, ran the checks, measured the usage. Two of three is shown as two of three, not as confidence.

Ranked by what it would cost you to be wrong

A priority score from production load, clean-core grade and S/4 impact, so the first hundred decisions are the hundred that matter.

Four hundred and forty-one at a time, if you want

Decide one object or every object matching a filter. Either way the reason is stored with the decision and the decision is dated.

04 · Convert

Before Forge rewrites a line, it writes the specification nobody ever wrote.

A sixteen-section technical specification, recovered from the code as it runs today: what it does, what it touches, what it posts, what it checks, what it costs to run. It is the document your original developer did not leave behind — and for most objects it is worth more than the rewrite.

It finds the bugs you have been running for years

In one 91-line pricing report: totals that mix currencies without converting, a sum of five arbitrary conditions with no defined business meaning, an authorisation check applied after the row limit so two users get two different answers, and a failure reported as an information message, so no batch job could ever tell error from success.

Every rule quotes the lines it came from

The specification ends in a traceability matrix: each rule, and the source lines it rests on, copied from the code Forge holds. Those quotes are checked against the source without a model — the prose is written by an agent, the evidence is verified by machine.

Test cases and an effort range, before you commit

Baseline tests written against the rules they cover, the SAP successor objects named for each obsolete one, and an estimate range drawn from a published table — so the business case is costed from the code, not guessed.

Hollow is not a pass.

The rewrite waits behind four of SAP’s own checks — syntax, activation, ABAP Unit and ATC with clean core. Until every one has actually run and actually passed, the approve button is not disabled as a courtesy; it is unavailable. Forge will not let you activate something it has only asked a model about.

The agent’s account is labelled as the agent’s account

The summary of what changed and why is marked as written by the agent about its own work, with “review before approving” attached. Forge never passes a model’s self-report off as a finding.

Old and new, side by side, with the changes marked

The original as SAP holds it against the candidate, every changed block marked in the ABAP itself with a reference you can grep for. Capture the original’s output first and compare the two runs.

05 · Create

And what you never had, from a requirement someone typed.

Not every gap is a legacy object. Genesis takes a plain-language requirement — a few sentences a controller could write — and carries it to a functional specification, your approval, code checked on SAP, and activation. Five gates, and the requirement is stored exactly as given, with a hash, so what was built can always be read back against what was asked.

Stored exactly as given

The requirement keeps its own SHA-256. The specification and the code both trace to that text, and nobody can quietly edit the brief after the fact.

A specification you approve, not a prompt you hope about

Scope, selection criteria, business rules, output, errors, authorisations, test scenarios — and the open questions the requirement did not answer.

It ends as a real object on SAP

Checked on the system and activated into a named package, through the same lane and the same gates as everything else Forge writes.

Everything on this page says where it came from.

The hardest problem with an agent on an SAP estate is not capability, it is knowing which claims to trust. Forge answers it the dull way: every statement in the product is badged by origin, and the badges are not decoration.

Read from the system

Measured. No model involved, and the read is dated.

Typed by a person

Stored as written, hashed, attributed and timestamped.

Written by the agent

Useful, cited to line numbers, and never mistaken for proof.

Checked on SAP

The only badge that unlocks approval, because it is the only one SAP signed.

Forge is a face of the record, not a separate tool.

The Brief rules on the process; Forge reads the system, decides each object and writes the code; Manage tracks the work and the gates. A ruling made in Explore is the reason a line of code exists in Realize — and the reason an object was retired instead of rebuilt.
